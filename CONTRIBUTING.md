# Contributing to the Workbench

First off, thank you for considering contributing! Whether you're fixing a bug, improving documentation, adding new visual canvas nodes, or writing tests, your help makes this tool better for the entire Minecraft modpack and server community.

The project is licensed under **GPL-3.0** (app + companion mod); standalone utility libraries may use permissive licenses. By contributing you agree that your contributions are licensed accordingly.

---

## Our Core Philosophies

To keep this project fast, reliable, and maintainable, we adhere to a few strict architectural principles:

1. **Modularity First (Pluggable Drivers):**
   - External dependencies—such as launcher integration, file system storage, and IPC networking—sit strictly behind abstract driver interfaces (e.g., `LauncherDriver`).
   - Want to add support for a new launcher or storage backend? You only need to implement a new driver without touching core business logic.

2. **Strict Separation of Concerns:**
   - **Parsers & Core (`/src/core/`):** Pure, deterministic functions with zero UI or IPC dependencies.
   - **System Drivers (`/src/drivers/`):** Encapsulated I/O, IPC sockets, and process execution.
   - **UI Layer (`/src/components/`):** Canvas and node rendering engines. UI components must never perform raw disk I/O directly.

3. **100% Local & Offline-First:**
   - The core workbench must operate with zero mandatory network calls, cloud authentication, or remote LLM requirements.

4. **Safety & Comment Preservation:**
   - User workspace files must never be corrupted by partial writes (always use atomic file swaps via `.tmp` staging).
   - Custom formatters (such as `.snbt` and `.json5`) must preserve original user comments and custom indentations.

## AI-Assisted / "Vibecoded" Contributions

We actively embrace AI-assisted workflows (e.g., OpenCode, Cline, Cursor, Copilot). Whether code was typed by hand or generated by an LLM, **we evaluate all contributions by the same quality standards**:

- **Tests must pass:** Generated code must come with unit or parser test coverage where applicable.
- **No monolithic dumps:** Code should remain modular, readable, and split across small, focused utility files.
- **Documentation is code:** If your PR adds or changes a feature, CLI flag, or IPC channel, you must update the relevant documentation in `/docs` or the `README.md`.

*Note for AI coding agents: Please review `AGENTS.md` in the project root for strict execution constraints and file safety boundaries.*

## Development Setup & Workflow

### Prerequisites
- **Node.js** (v18+ recommended) & **pnpm**
- **Prism Launcher** (installed locally for testing launcher execution and instance pathing)

### Getting Started

1. **Fork & Clone the Repository:**
   ```bash
   git clone https://github.com/your-username/your-repo-name.git
   cd your-repo-name
   ```

2. **Install Dependencies:**
   ```bash
   pnpm install
   ```

3. **Start the Local UI Dev Server:**
   ```bash
   pnpm dev
   ```

4. **Run the Test Suite:**
   ```bash
   pnpm test
   ```

## Git & Pull Request Guidelines

To keep our commit history clean and predictable, we follow **Conventional Commits**:

### Commit Format

```
feat: add marquee multi-select to quest canvas
fix: handle EBUSY file lock error during Windows staged sync
docs: update Prism Launcher pathing setup instructions
test: add unit tests for FTB Quests SNBT number suffix parsing
```

### Opening a Pull Request (PR)

- **Branch Naming:** Create a short, descriptive branch off `main` (e.g., `feature/quest-inspector` or `fix/windows-socket-fallback`).
- **Atomic Commits:** Keep commits small and logically separated.
- **Check Safety:** Ensure `pnpm test` and `pnpm lint` pass cleanly before submitting.
- **Description:** Describe what changed and why. If your PR includes visual canvas changes, include a quick screenshot or GIF!
